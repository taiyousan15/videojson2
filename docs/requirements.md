# 要件定義書（VideoJSON）

## 0. この文書の目的
VideoJSON が「何をできるようにするか」を、初心者でも理解できるようにまとめます。
実装の前提として、ここに書いたことが最優先です。

## 1. 何を作るのか（概要）
元動画を解析して「流れ（構成）」を JSON にします。
その構成をベースに、台本（narration）・音声・人物（見た目）を差し替え、
似たテンポ感の "別内容の動画" を作る仕組みを作ります。

例（目標イメージ）:
- 元動画: 雑談形式で3つのポイントを話す動画
- 新動画: 同じように「導入→3ポイント→まとめ」だが、テーマ・話す内容は別の台本に置き換える
- 声: ユーザー本人の声の音声を利用（本人がOKなら）
- 見た目: ユーザーが提供した画像を元にした人物、またはアニメ風/3D風など別スタイル

## 2. 想定ユーザー
- クリエイター（初心者〜中級者）: 動画を効率よく量産したい
- 運用担当: テンプレを使って複数企画を回したい
- 管理者: 権利・安全・コストを管理したい

## 3. 重要な用語（かんたん説明）
- structure.json（Event JSON）: 元動画の流れを区間ごとに分けた設計図
- narration.md: 台本（structureの区間IDに沿って書く）
- render.json: 自動編集に使う設計図（後でレンダリング処理に渡す）
- ジョブ: 「解析」「音声生成」「レンダリング」など、時間がかかる処理の単位
- アセット: 画像・音声・動画・字幕などの素材

## 4. ユーザーがやりたいこと（ユーザーストーリー）
US-01: ユーザーは YouTubeリンク/動画ファイルを渡して、構造（structure.json）を作りたい
US-02: ユーザーは structure.json を元に台本（narration.md）を自動生成し、編集したい
US-03: ユーザーは 自分の音声ファイル を渡して、その声で喋る音声を作りたい（本人の声）
US-04: ユーザーは 画像（人物の見た目）を渡して、話している風に見せたい（リップシンク）
US-05: ユーザーは 元動画のテンポや構成を参考にしつつ、中身を差し替えた新動画を作りたい
US-06: ユーザーは アニメ風/3D風など複数バージョンを作り、選択肢として比較したい
US-07: ユーザーは 生成結果を差分修正し、最小の手直しで改善したい

## 5. 機能要件（何ができる必要があるか）
### 5.1 解析（元動画 → structure.json）
- YouTubeリンクまたはアップロード動画を取り込める
- 元動画を時間区間（セグメント）に分割し、各セグメントの要点を出せる
- 画面内テキスト（テロップ）の抽出（可能なら）を含める
- 人物（話者/登場人物）の区別（可能なら）を含める
- 出力は structure.json として保存できる

### 5.2 台本（structure.json → narration.md）
- structure.json のセグメントIDに対応した台本を生成できる
- 台本はユーザーが編集できる（UIまたはファイル）
- "元動画のコピー" にならないように、台本は必ず書き換える前提で設計する

### 5.3 音声（narration.md → 音声）
- ユーザー本人の音声ファイルを利用できる
- 台本に沿った音声を生成できる（TTS / 音声変換 どちらでも）
- セグメントごとに音声を分割して扱える

### 5.4 人物（画像 → リップシンク）
- ユーザーが提供した画像を利用できる
- 台本音声に合わせて口パク（リップシンク）ができる（可能な範囲で）
- "本人の許可がある素材のみ" を前提とする

### 5.5 レンダリング（render.json → 動画）
- structure/narration/アセットから render.json を組み立てる
- render.json を元に、最終動画を生成できる（FFmpeg等）
- テロップ、字幕、BGMなどを差し込める

### 5.6 バリエーション生成
- 同じ台本・同じ構成で、アニメ風/3D風などスタイル違いを複数出せる
- 生成バージョンを比較できる（どこが変わったかが分かる）

### 5.7 検証（Claude生成ミスを即検知）
- structure.json と render.json を機械的に検証できる（JSON Schema）
- examples/ の最小サンプルでCI動作確認ができる
- schema_version を上げたときの移行ルールがある（migrations.md）

## 6. 非機能要件（品質・運用）
- 失敗したジョブは原因が分かるログを残す
- 再実行（リトライ）ができる
- コストが高い処理（生成系）に上限をかけられる設計にする
- APIキー等の秘密情報をコードに直書きしない

## 7. 権利・安全（必須）
- 第三者の声・顔を勝手に真似する機能は、許可がない限り運用しない
- 元動画を参考にしても、台本と表現は必ず作り替える
- 使用素材の権利（利用許諾/ライセンス）を確認できる導線を用意する

## 8. 受け入れ基準（最低ライン）
1) examples/minimal/structure.json が schemas/structure.schema.json に通る
2) examples/minimal/render.json が schemas/render.schema.json に通る
3) npm run schema:validate がCIで失敗せず通る
4) structure→narration→render の最小フローが docs に書いてあり、初心者でも手順が追える
